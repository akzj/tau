## §F — Q-First 5 答持久化

### Q1 — `Compat any` 弃用力度
**回答**：维持 ❌（"docs as spec"原则字面违反）。phase2 §3 R1 (b) 明确"禁 `interface{}` / `any` 在公开 API 签名"——`Compat any` 字面命中。**v1.2 修订**：替换为 `Compat WireCompat`（sealed interface），docs 加注"concrete types: OpenAICompletionsCompat | AnthropicMessagesCompat | OpenAIResponsesCompat (sealed)"。

### Q2 — extractFileOpsFromMessage 最终标记
**回答**：A（➕ 补充项）。docs 行 73 "convention-based, not schema-enforced" 是 pi 反例描述；tau 必须 divergence。phase2 §2.6 + §5.1 没列 FileOperations 注入接入点——是真的设计补充：产品层（compaction）需要从 tool result 提取 file ops，tau 应让产品层显式注入 `FileOperationsExtractor func(ToolResult) []FileOp` 而非按 tool name 硬扫。**进 Phase 4 重审清单 R4**。

### Q3 — onPayload/onResponse evidence
**Q3a evidence**：StreamOptions 字段，不是 Hook。pi `types.ts:109` `onPayload?: (payload, model) => unknown | undefined | Promise<...>;` `types.ts:114` `onResponse?: (response, model) => void | Promise<void>;` 5+ provider 一致调用（`openai-completions.ts:145, 157`）。grep `registerHook|onPayloadHook|hooks.onPayload` 0 结果。形态与 phase2 §2.4 现有 `TransformToolName` 完全同类（caller-injected per-request callback）。
**Q3b 倾向**：加（合 v1.2）。形态一致性 + 真实驱动场景 + C7 不破。
**Q3c**：N/A（Q3a 已确认是字段）。
**v1.2 范围结论**：加 `OnPayload func(payload any) (any, error)` + `OnResponse func(resp HTTPResponse)` 到 StreamRequest。HookSet 不动。

### Q4 — pi OpenRouterRouting 嵌 OpenAICompletionsCompat
**回答**：是 pi 自己的设计错（应是 vendor-level）。OpenRouter 是 vendor，wire api 是 openai-completions（pi 自陈 §4.3 \"all OpenAI-compatible vendors share the openai-completions plugin\"）。把 vendor-specific routing 嵌进 wire-level compat type 让 30 个 vendor 共享一个 schema = 最低公分母反模式。**v1.2 VendorConfig 应含 vendor-typed Routing 字段**：`AnthropicVendorConfig.Routing` 不存在，`OpenRouterVendorConfig.Routing OpenRouterRouting` 才有。与 form B 天然契合。
